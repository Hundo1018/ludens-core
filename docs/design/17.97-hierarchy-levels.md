# 17.97 階層(ChildOf)與換關卡

狀態:草案(2026-11-16),待決定。ROADMAP 編號 17.97 為暫定;本筆記核准後才加入 ROADMAP、子系統表並開 issue。
範圍:ludens-core 的部分(宿主入口上的實體、`ChildOf` 階層、剛體與實體的連結、換關卡的操作)。ludens-engine 的部分
(場景檔的節點列、prefab 巢狀、`GameMode` 的關卡切換、編輯器場景樹)列在最後一節,由 engine 另開設計。

## 動機(來自 ludens-playground 的實作)

- playground 的 frontier 世界沒有用到 ECS:整張地圖是一個 `EmbedWorld`,五個區域寫死在 `frontier/world.mojo`(`zone_of`),
  物件是 `WorldPartition` 的 `BodySpec`,沒有父子關係。全 repo 只有 `app/crowd.mojo` 用 ECS。
- 遊戲碼有 8 處直接取用 `world.scene`(`DynamicCharacter`、`SpringArm`、`WorldPartition.update`、`Rope` 的 attach / tie / step),
  因為這些 API 收 `ContactScene6`,而 `EmbedWorld` 沒有對應入口。
- 繩子與旗幟布料完全在 `EmbedWorld` 之外(布料在另一個 `flag_scene`),所以不在 `save`、雜湊或任何場景描述裡。
- 布娃娃剛體與角色網格的對應、角色與其附屬物的關係,全由遊戲以平行陣列自行維護(`rag`、`rag_rest_pos`…)。
- 範例沒有換關卡:按 R 是傳送回 hub。

## 決定 1:宿主只有一個入口

現況有兩個平行的入口:`EmbedWorld`(無實體,所有宿主都在用)與 `gameplay.Runtime`(有實體與剛體連結,只有範例在用)。
若只在 `ecs/` 內統一 `ChildOf` 而宿主碰到的東西仍沒有實體,會重複「API 沒有使用者」的問題。

- **(a)(建議)`EmbedWorld` 加入實體**:內含一個 ECS `World` 與 `RelationStore`;每個剛體是一個實體(`RigidBodyRef`),
  也可以有不帶剛體的實體(群組根、觸發區、掛點)。現有以剛體 handle 為主的 API 不變,另加以實體為主的 API。
  `Runtime` 的姿態同步、`carry_to` 併入;C-ABI 以新增函式提供實體操作,`abi_v0.txt` 只追加。
- (b)`Runtime` 成為入口,C-ABI、`scene_io`、編輯器、playground 改用它。改動面大,且 `Runtime` 未經任何宿主使用。

## 決定 2:`ChildOf` 是唯一的父子關係

規則:

- **一個實體最多一個父**:`set_parent(child, parent)` 先移除舊的 `ChildOf` 邊;`parent` 是 `child` 的子孫時拒絕(丟錯,世界不變)。
  `RelationStore` 本身允許多個目標,所以由這個函式負責,`relate(CHILD_OF, …)` 不對外。
- **刪除連帶子孫**:`despawn(e)` 依反向索引(`sources(CHILD_OF, e)`)由下而上刪除子孫,並清除每個實體的所有關係、移除其剛體。
  `World.despawn` 與 `Commands.apply` 走同一條路徑;目前只有後者清關係,刪了父的世界會留下懸空的邊。
- **`Parent` 移除**:`Hierarchy.build` 改從 `ChildOf` 建,輸出格式不變,三種傳遞策略(full / dirty / motor)不改。
  遷移時以 parity 測試證明舊路徑與新路徑的世界矩陣逐位相同,並在 `bench_transform` 加一列(架構定律 v2)。

## 座標系

- `Transform` 存相對父的局部 TRS 與快取的世界矩陣(現況)。根節點的局部即世界。
- **動態剛體是模擬根**:物理決定它的世界姿態,每 tick 寫回 `Transform`;若它有父,局部 = 父世界矩陣的逆 × 世界姿態。
  它的子孫(網格、掛點、觸發區)跟著它走。
- **靜態 / 運動學剛體掛在會動的父下**:每 tick 以運動學目標跟隨父的世界姿態,不用 `teleport`(瞬移會讓接觸失去連續性)。
- **剛體與剛體之間的連接用關節**,不用階層。兩個動態剛體互為父子時,子的姿態仍由物理決定,`ChildOf` 只表示從屬(刪除、群組、事件冒泡)。

## 互動的傳遞與群組

- **事件冒泡**:接觸、觸發、遊戲事件先送到目標實體,再沿 `ChildOf` 往祖先傳;任一層可停止。以一個系統處理佇列,順序固定
  (事件產生順序,同一事件由子到根),所以結果決定論。例:手部碰撞體的接觸冒泡到角色根,由角色的處理器決定反應。
- **群組**:兩種,依用途選擇。
  - 標籤元件(無欄位的 `ComponentType`):對應 Unity 的 tag,查詢最快。
  - `MemberOf` 關係指向一個群組實體:對應 Godot 的 group,可在執行期增減成員,`sources(MEMBER_OF, g)` 取成員。

## 換關卡

**做法:同一個世界內替換子樹**,不另開世界再搬運。

- 每個關卡有一個關卡根實體;載入的場景成為它的子樹。
- 標記 `Persistent` 的實體(玩家、跨關卡的道具)掛在世界的常駐根下,不屬於任何關卡。
- 換關卡 = `despawn(舊關卡根)`(連帶子孫、剛體、關節、關係),再 `instantiate(場景, 新關卡根)`。
- `LevelDirector` 的協定不變:`request` → 宿主取 `LoadLevel`、讀場景檔 → 呼叫上面的替換 → `loaded`。載入中事件暫存、不可存檔的規則照舊。
- 好處:常駐實體的 handle 不變;不受 `carry_to` 只能搬方塊與球的限制。`carry_to` 保留給「跨世界」的少數情況,不再是換關卡的路徑。

**決定論的限制**:刪除後剛體槽位會被重用,所以「先載 A 再換 B」的槽位分配,與「新世界只載常駐實體與 B」不同,雜湊也不同。
驗收因此只要求:
- 同一操作序列在不同次執行、原生與 wasm64 之間逐位相同;
- 卸載後 A 的剛體、關節、關係數為 0;
- 常駐實體在替換前後狀態逐位相同。

若要「與重新建立的世界逐位相同」,需要正規化的槽位分配(換關卡時壓縮重排並回傳新舊 handle 對照),列為開放問題。

## 相依與缺口

- `scene_io` 目前拒絕匯出破碎物件與水;playground 的 quarry 有破碎牆,所以區域要變成關卡檔,需先補破碎物件的場景片。
- 繩子、布料在 `EmbedWorld` 之外,不在場景、存檔或雜湊裡。含它們的關卡需要它們成為世界功能,或成為實體擁有的元件(由系統步進)。
- 引擎事件表以 `@i`(場景中第 i 個剛體)指稱物件。prefab 巢狀會讓索引失效,所以節點需要場景內的局部 id,在實例化時重新對應。
- `save` / `hash` 要涵蓋實體、`ChildOf` 與群組(17.95 的 `test_save_coverage` 加對應項目)。

## 工作切片(core)

1. `Hierarchy` 改從 `ChildOf` 建;`set_parent`(單一父、拒絕循環);單一刪除路徑連帶子孫。parity 測試(`Parent` 與 `ChildOf` 的世界矩陣逐位相同)
   與 `bench_transform` 一列;之後移除 `Parent`。
2. `EmbedWorld` 內含實體:剛體即實體、姿態同步、無剛體的實體、`save` / `load` / `hash` 帶實體與關係;C-ABI 追加實體函式。
3. 座標規則:動態剛體寫回、掛在會動的父下的運動學跟隨。
4. 事件冒泡與群組(標籤、`MemberOf`)。
5. 換關卡:關卡根、`Persistent`、`instantiate(場景, 父)`、替換操作接上 `LevelDirector`。

## 驗收(全部切片完成時)

- 階層:循環被拒、刪父連帶子孫且無懸空關係、`Parent` 與 `ChildOf` 路徑世界矩陣逐位相同。
- 事件:三層階層中,子的接觸依子 → 根順序到達;中間層停止後根收不到。
- 換關卡:A → B → A 三次替換,每次卸載後 A 的剛體、關節、關係數為 0;常駐實體逐位相同;同序列兩次執行、原生與 wasm64 雜湊相同。
- 成本表:實體數 1e3 / 1e4 的替換耗時與傳遞耗時。
