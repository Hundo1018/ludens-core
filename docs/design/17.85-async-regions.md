## 問題

今天所有 island 共用一個全域 tick。`ContactScene6.step` 每步做一次全場的配對收集(`physics/solver6.mojo:3063`)、
一次 island 標籤(`:3081`),island 之間只在「求解」這一段平行(`_solve_islands_parallel`,`:3492`),
之後的 sleep、NaN 隔離、事件、`step_index += 1` 又是全場一次(`:3138-3150`)。17.85 的 tier 只能讓 island
**跳過**某些步(`_step_tiered`,`:3323-3379`:island 在 `(step_index + first) % period == 0` 時以 `period * dt` 補算),
不能讓它在時間上領先或落後別的 island(17.100 第 6 項起,`cfg.parallel` 時到期的 island 經 `cfg.dispatch` 分派(`_TierTask`),但仍在同一個全域 tick 內)。

量到的上限都來自這個全域同步:

| 量測 | 數字 | 出處 |
|---|---|---|
| island 平行,16 塔 64 體 | 表中最快 254.6 µs/step,對序列 434.4 µs 為 1.71×(報告文字寫約 1.6×);約 4 workers 以上持平 | `BENCHMARK_REPORT.md:3486-3488, 3520-3532` |
| 由 Amdahl 反推的平行比例 | 約 40 %;其餘 60 %(broadphase、標籤、姿態積分、sleep、快取)是序列 | `BENCHMARK_REPORT.md:3486-3491` |
| 17.85 tier,1e4 體 | 未分級 292.8 ms/step → DistanceTiers 59.6 ms(4.9×);論述指出收集每步全額支付 | `BENCHMARK_REPORT.md:5437-5440, 5457-5458` |

目標:讓一個**區域**(若干 island 的聯集)在另一個 worker 上領先或落後另一個區域 k 個 tick,而最終世界與
「全場同步一起步進」(以下稱 lock-step 參考)逐位相同。例:玩家附近的區域每個 wall-clock frame 都要推進一個 tick;
50 m 外的另一堆箱子可以晚 4 tick 才算完,不必讓近區等它。

## 安全條件:多步光錐

在同步點 tick t,區域 R 不聽區域 S 的消息而從 t 推進到 t + k 的充分條件:

```
gap_t(R, S) > D_R(k) + D_S(k) + base
D_X(k)     = V_X * k*dt + 0.5 * |g| * (k*dt)^2 + W_X * r_X * k*dt
```

且 R 與 S 之間沒有任何下面列出的非幾何耦合。各項定義:

- `gap_t(R, S)`:t 時 R 所有動態成員的 collider AABB 聯集與 S 的聯集之間的距離。用 broadphase 使用的同一個 AABB
  (`colliders` 的形狀盒,不含邊距),兩邊各取一個聯集盒即可;聯集盒過大只會讓條件更保守。靜態與 sleeping 的 body
  不屬於任何區域(它們不動),所以不算進 gap;兩個區域可以共用同一塊地板。
  例外:sleeping body 被接觸就會醒(`refresh_islands` 的喚醒規則,`physics/islands.mojo:68-75`),醒了就會動。一個 sleeping
  island 若同時落在兩個區域的 `D(k)` 範圍內,兩區必須合併;只落在一區範圍內的,視為該區成員。
- `V_X`:同步點 t 時 X 內的 `max |v_i(t)|`,只是**預測量**(重力造成的增速已在 `0.5 |g| (k dt)^2` 項)。它不是 k 步期間的上界:
  接觸衝量可以把重物的速度轉給輕物,推出偏壓受 `max_push_speed` 限制(`solver6.mojo:3030`)但會加速,恢復係數、
  關節驅動也會。可證明的上界只有一種:`max_lin` 速度上限(`physics/body_set.mojo:127`,在 `_props_post` 套用,
  `solver6.mojo:1733-1748`)。但它在步末才夾,步內子步的速度可以暫時超過,所以連它也要再驗證。
- `W_X r_X`:角速度上界乘以最大旋轉半徑(CCD 的 `|w| r` 項)。`speculative_margin` 沒有這一項,單步時邊距的 `base`
  吸收了它;k 步時旋轉造成的表面位移和 k 成正比,不能省。
- `base`:`SolverConfig.margin_base`(預設 `SPEC_BASE` = 0.02 m)。配對門檻是 `base + (|v_a| + |v_b|) dt`,`base` 只出現一次
  (兩邊各 `base/2`,`fat_aabb`);各 tick 的速度項已含在 `V_X * k*dt` 內(前 k-1 tick 的位移加最後一 tick 的邊距)。
- 哪些項是證明、哪些是假設:式子在「k 步內速度不超過 `V_X`、角速度不超過 `W_X`」的前提下成立;這個前提沒有證明。

數字例:dt = 1/60 s、k = 4、兩區最快 5 m/s、重力 9.8、旋轉項 0.5 m × 2 rad/s,`D = 5·0.0667 + 0.5·9.8·0.0044 + 1·0.0667 ≈ 0.42 m`,
所以兩區聯集盒相距 `0.84 + 0.02 ≈ 0.86` m 以上就可以放行 k = 4。50 m 外的兩堆箱子在 k = 8 時(`D ≈ 0.89 m`)也遠遠滿足。

### 因為 V 沒有可證明的上界:預測 + 事後驗證

上式用來**選 k**(預測),不用來保證正確。正確性由同步時的事後驗證保證:

1. 每個區域在推進時逐 tick 記下自己成員 `fat_aabb` 的聯集,即每個 body 以 `base/2 + |v_i| dt` 膨脹(該 tick 實際的速度)。
   每軸上兩邊的膨脹相加正好是配對邊距,所以「區域聯集盒」有明確定義,與 broadphase 檢查同一件事。
2. 兩個區域都到達 t + k 後,逐 tick 比較兩者的聯集盒。若每一 tick 都不相交,lock-step 在這 k 步內不會產生任何跨區配對
   (配對的必要條件是膨脹後的盒相交,`contact_gen.mojo:676-720`),所以兩區的結果就是 lock-step 結果的子集,逐位相同。
3. 若某 tick 相交,兩區都載回 t 的快照,改以 lock-step 重算這 k 步,並記一筆 counter(暫名 `ASYNC_CONE_MISS`)。

這是「(a) 保守」的形式:沒有東西在驗證前被提交,所以重算只回到上一個同步點,不會連鎖。代價是一個區域的結果在驗證完成前是暫定的
(開放問題 2)。只有在有可證明的速度上界時(下一節),近區的結果才不是暫定的。

## 決定論:結果要等於什麼

契約:同工具鏈、同架構逐位相同(`docs/ROADMAP.md` §17.16 決定),派發器不得改變結果(`scheduler/dispatch.mojo:15-18`)。
非同步步進的參考是 **lock-step 參考**:同一個世界,不分區,以序列派發器每 tick 步進一次。

兩種做法的最終狀態都等於 lock-step,差別在成本:

| | (a) 預測 + 驗證(建議) | (b) 樂觀 + 回滾(Time Warp) |
|---|---|---|
| 推進條件 | 光錐預測放行才推進 | 各區自由推進,收到「過去」的跨區消息時回滾 |
| 回滾範圍 | 最多回到上一個同步點(k 步),只涉及相交的區域;沒有跨區消息可作廢,不連鎖 | 可連鎖:R 回滾使它送給 S 的消息作廢,S 再回滾 |
| 快照 | 每個同步點一份整場快照(`scene_to_bytes` 已有) | 每區每 tick 一份區域快照(今天沒有);17.16 的 3 玩家小場景全快照即 4952 B / frame |
| 宿主可見結果 | 驗證前是暫定的 | 全域虛擬時間(GVT)之前是暫定的 |
| 參考成本 | — | 17.16 rollback:6 tick 延遲下每 frame 2.19 ms,240 tick 重算 4471 tick |

兩者都只有在**有可證明的速度上界**時,近區的結果才能立即提交:即所有動態 body 都有 `max_lin` / `max_ang`,且上限改在子步套用
(目前在步末,`solver6.mojo:1733-1748`;改動會改 golden)。此時光錐條件本身就是證明,(a) 不需事後驗證。
選 (a) 的理由是回滾有界、不需要區域快照,而且在有上界的情況下自然退化成純保守做法。

- **區域劃分與 k 只能是模擬狀態的函數**:island 標籤、姿態、速度、tick、設定。不得讀牆鐘、執行緒時間或工作完成順序。
  同一個狀態必須得到同一組區域與同一個 k,否則重播(17.39)與 rollback(17.16)會在不同排程下走不同的路徑。
  例:區域編號 = 區域內最小 slot,k = 光錐允許的最大值與上限 `k_max` 取小。
- **兩種實作方式待決**(開放問題 1):(i) 每區是一個子 `ContactScene6`,body 編號必須是全場編號的保序映射,否則配對排序
  與 union-find 根會變;(ii) 同一個 `ContactScene6` 內以區域遮罩步進一部分 body,每區自己的 `step_index`、快取區段與
  broadphase 子集。(ii) 不需要搬資料,但目前 `step_index`、`cache`、`counters` 都是場景層級的單一欄位(`solver6.mojo:323`)。

## 與既有功能的組合

- **17.85 tier**:區域與 tier 正交。一個區域內的 island 可以各有 period;條件是光錐用 `period * dt` 計算該 island 的位移。
  觀察:`_step_tiered` 以 `h = dt * period / substeps`(`:3368`)補算 `period` 步,但配對是以 `spec_dt = dt` 收集的
  (`:3063`),邊距只涵蓋一個 dt。這和本設計的 k 步邊距是同一個問題,先以測試確認現況是否有跨 island 的漏接(開放問題 4)。
- **睡眠**:sleeping island 不屬於任何區域,當作靜態處理(不動、不需同步)。被喚醒時(接觸到某區),併入該區;
  喚醒只會在同步點或區內發生,因為喚醒來源一定是與它接觸的某個區域。
- **`AggregateTiers`**:period 0 的凍結 island 與 sleeping 同樣處理;`ClusterProxy` 的 `lo / hi`(`gameplay/tiers.mojo:233-242`)
  可直接當作它的 gap 盒。
- **`WorldPartition`**:cell 是自然的區域邊界候選,但不能直接用:區域必須是 island 的聯集,cell 會切開一堆箱子。
  載入 / 卸載是同步屏障。
- **rollback netcode(17.16)**:`RollbackPeer` 回滾到 tick t 時,非同步排程從 t 的快照重新決定區域與 k;因為兩者是狀態的函數,
  重算的排程與原來相同。區域劃分也可以給 17.16 的 interest management 使用(只送與某玩家同區或相鄰區的 body)。
- **wasm Web Worker**:據呼叫端 2026-11-23 的探測(未入 repo,無紀錄可引),`DISPATCH_HOST` + Web Worker 與單執行緒雜湊相同,
  但比單執行緒慢;當時的原因是每次 sweep 都為 island 配置一個 `SweepCache`。17.100 第 6 項改為每個 island slot 重用一份(`island_sweeps`),
  這次探測早於該修正,要重量。區域步進的工作粒度是一個區域的完整 tick(含收集),比一個 island 的求解大得多,分派成本占比較低。

## 量測計畫(實作前)

目的:在不改引擎的前提下,量出光錐放行的比例與加速上限,決定值不值得做。

場景(新 probe `benchmarks/probes/async_cone_probe.mojo`(待建),沿用 `bench_tiers` 的兩箱堆疊產生器;`bench_crowd` 是導航代理,不是剛體,不能用):

| 場景 | 內容 |
|---|---|
| S1 兩堆 | 兩堆各 64 箱(4 × 4 × 4),中心相距 50 m;其中一堆每 2 s 被一顆 10 m/s 的球打一次,保持活躍 |
| S2 20 群 | 2000 箱分 20 群(每群 100,兩箱堆疊),群心在 200 m × 200 m 上的 5 × 4 格點,群內有一個持續推動的運動學板 |
| S3 交會 | S1 的兩堆以 3 m/s 相向推進,直到接觸;量放行率怎麼隨 gap 下降 |

每個場景 600 tick(dt = 1/60),每 tick 以 lock-step 步進,離線計算:

1. 區域:以 island 標籤為節點,gap 小於 `D(k_max)` 的 island 合併成一區(union-find)。報告區域數的分佈。
2. 對每一對區域與 k ∈ {2, 4, 8}:以 t 時的速度算 `D(k)`,判定是否放行;再以 lock-step 的實際軌跡做事後驗證
   (步驟「預測 + 事後驗證」的第 2 點)。報告:放行比例、預測放行但驗證失敗的比例(錯誤放行率)、預測拒絕但實際分離的比例(保守度)。
3. 加速上限(關鍵路徑):求解段用 17.80 (c) 的逐 island trace lane(`_solve_islands_parallel` 的 `add_lanes("island", …)`,
   `solver6.mojo:3520-3537`)。收集段在 trace 裡是一個全場的 `collect_pairs` 區段(`:3062`),沒有分區;以估計代替:
   區域收集成本 = 區域的 body 數 × 每 body 成本 + 配對數 × 每配對成本,兩個係數由全場 `collect_pairs` 區段對 body / 配對數迴歸得到。
   一個同步窗內的上限 = Σ 工作 / max(單一區域的工作),再以 Amdahl 扣掉仍是全場一次的部分(同步點的劃分與驗證)。
   與 `bench_islands` 的 1.7× 平台比較:若 S2 的上限低於 2×,本設計不值得做。
4. 每 tick 成本:量光錐判定本身(區域聯集盒 + 兩兩比較)的成本。目標(待量)是區域數 20 時在 10 µs 以下。

需要先修的量測缺口:`bench_tiers` 目前只有每步總時間,沒有分區成本;probe 要自己累計。
