# 17.89 wasm 平台:以 wasm64 為跨平台交付形態

狀態:規劃(2026-11-01)。可行性已實測,PoC 保存在 `tools/wasm/poc/`(實測紀錄 `tools/wasm/poc/FINDINGS.md`)。

## 決定

- **方向 C 不變**:本庫仍是被宿主嵌入的模擬函式庫。改變的是交付形態:除了原生共享庫(`build/libludens.so`)與
  Python wheel,新增 **wasm64 模組**作為跨平台通用產物,讓瀏覽器、Node / Deno、WASI 執行環境(wasmtime)與能載入
  wasm 的宿主引擎使用同一份二進位。
- **wasm 的匯出介面就是 12.1 C-ABI**(`embed/capi.mojo`、`embed/ludens.h`);不另設一套 API。
  `abi_v0.txt` 的凍結清單同樣適用於 wasm 匯出。
- **wasm64(memory64)為主線**;wasm32 要等 Mojo 本身能以 32 位元指標 lower(見「等 Modular」)。

## 實測結果(2026-11-01,Mojo 1.2.0)

| 項目 | 結果 |
|---|---|
| Mojo 原生 wasm 目標 | 無:`--target-triple wasm32-wasip1` → `No available targets are compatible`;`--print-supported-targets` 無 wasm |
| 整套 C-ABI 的 IR | `mojo build --emit llvm embed/capi.mojo`:42 MB、846 個函式、24 個外部 declare(Mojo runtime 配置 / 診斷、執行緒池、7 個 libc) |
| 重定目標 | Modular 的 LLVM 為 24.0.0git;conda-forge LLVM 23.1.4 的 `opt -O3` / `llc` 只需換 triple / datalayout、去掉 target 屬性、stub 掉 `llvm.x86.sse.{st,ld}mxcsr`(`retarget.py`)。系統 LLVM 18 需 9 處文字改寫,且其物件與 wasm-ld 24 連結後 `call_indirect` 型別不符 → **llc 與 wasm-ld 必須同一個 LLVM 主版本** |
| 連結 | `wasm-ld -mwasm64`(不用 `--allow-undefined`)+ 約 150 行 C shim(`shim.c`:配置器、`write` / 時鐘轉宿主匯入、執行緒池回 1、`sinf` / `cosf` 由宿主提供)→ 1 381 304 B(gzip 323 426 B),4 個宿主匯入 |
| SIMD | `Vec3` = `SIMD[f32, 4]` 直接對應 wasm `f32x4`(模組內 15 746 個 f32x4 運算) |
| 位元一致 | wasm64 的世界雜湊 = 原生 `--target-cpu x86-64`(無 FMA)的雜湊:12 體 240 tick 皆為 `4624da7477e83eff`(作者以 `run64.py` / `run_native.py` 重跑確認);原生帶 FMA 為 `b54cefb78d616c8`。1012 體時,宿主的 `sinf` / `cosf` 用 glibc 才相同,用 JS `Math.sin` 則不同 |
| 執行環境 | node 22 不支援 table64(`CompileError`);node 24、wasmtime 50 可跑 |
| 速度(單核,1012 體) | 原生 6.18 ms/tick、node 24 9.31(1.5×)、wasmtime 25.8(4.2×) |
| wasm32 | 同一份 IR 改 32 位元 datalayout,未優化時可跑,`opt -O3` 後在 `ld_world_create` trap:Mojo 編譯期已把指標大小定為 64 位元 |
| 未測 | CCD、軟體、導航、射線、存讀檔、宿主回呼:已連結但未執行 |

上游:modular/modular #4729(啟用內部 LLVM 的 wasm 目標)、#5367(原生 wasm 支援)皆 open、已分流,無承諾日期;
1.2.0 的 roadmap 未提 wasm。社群專案(noverby)採用同一條 IR → llc → wasm-ld 的 wasm64 路線。
瀏覽器 memory64:Chrome / Edge 133+、Firefox 134+ 已有;**Safari 未出**。

## 待決:浮點政策(需使用者決定)

wasm 沒有 FMA 縮併(relaxed-simd 的 FMA 會破壞位元一致,維持關閉),因此 wasm 只能與**無 FMA** 的原生建置逐位相同。
但專案目前的測試與 golden 釘 `--target-cpu skylake`(帶 FMA;`scripts/run_tests.sh`、ARCHITECTURE §6、`flag_policy.py`),
`pixi run capi` 也用主機 CPU(帶 FMA)。三個選項:

| 選項 | 內容 | 代價 |
|---|---|---|
| (a) wasm 自有 golden | 與 aarch64 / macOS 相同的做法:`test_stdout.wasm64.txt`,跨目標差異由 17.76 的容差表管理 | 最小;但不建立「wasm 與原生逐位相同」的保證 |
| (b) 參考建置改為無 FMA | x86 golden 改釘 `x86-64`(無 FMA),wasm 以雜湊對它逐位比對 | 全部 x86 golden 重錄一次;原生少了 FMA 的速度 |
| (c) 引擎自帶 sin / cos 並關閉 FMA 縮併 | 三角函式由引擎的多項式實作,所有目標同一份;`contract` 關閉 | 改變所有 golden;跨 x86 / ARM / wasm 才有機會逐位相同 |

建議:先做 (a) 讓 wasm 進 CI,再以實測決定是否值得做 (c)。原 2026-10-09 決定(「決定論只承諾同工具鏈、同架構」)
與 (a) 相容;(b)、(c) 會擴大這個承諾,屬政策變更。

## 與其他條目的關係

- 17.76 平台可攜:wasm64 子句由本條接手;跨目標容差表與 `fp_probe --compare` 直接沿用。
- 13.9 批次多世界步進(⏸ 等平台決策):wasm 交付不需要它,維持 ⏸。
- GPU(第 7 層):wasm 版只交付 CPU 路徑;WebGPU 後端屬 W4。
